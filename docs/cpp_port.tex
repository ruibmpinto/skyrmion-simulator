\section{Overview}

The micromagnetic SAF skyrmion simulator under \code{src/skyrmion_simulator/simulator/}
(Python/NumPy) has been ported to C++17 under
\code{src/simulator_cpp/}. The C++ build produces a deterministic
simulator (\code{skyrmion_sim}), thirteen per-analysis sweep binaries,
and a parity test-suite that checks every ported function against its
Python counterpart to machine precision. Outputs remain NumPy
\code{.npz} archives, so all Python post-processing, plotting, and
animation scripts read the C++ results unchanged.

This document lists the Python$\leftrightarrow$C++ function equivalence,
explains how to build and configure runs, and reports a like-for-like
performance comparison on a $64\times64$ lattice.

\section{Function equivalence}

Table~\ref{tab:equiv} maps each Python function to its C++ counterpart.
Where several small Python field builders are fused into one C++ loop
(for cache efficiency) this is noted. The deterministic simulator, the
sweep layer, and the full stochastic-LLG path (thermal noise, the
Stratonovich--Heun stepper, connected-component diagnostics, production
scans, and the physics-validation gates) are all ported. The analytic
Thiele helpers and all plotting intentionally remain on the Python side.

\paragraph{Error contract.} The port follows a strict ``no silent
errors'' rule: every invalid input raises. Four cases where the Python
original previously emitted a silent NaN (or accepted an out-of-range
value) were aligned so Python and C++ now raise identically:
\code{skyrmion_center} on an empty core mask, \code{uniform_state} on a
zero-magnitude direction, \code{normalize} on a zero-magnitude spin, and
\code{skyrmion_profile} on a polarity outside $\{+1,-1\}$.

\paragraph{Free-boundary mask and single-layer mode.} The field
builders \code{effective_field} and \code{effective_field_demag}, the
relaxation \code{sweep::relax}, and the stochastic
\code{HeunStochasticStepper} all take an optional free-boundary mask (a
row-major \code{ny*nx} array of 0/1 flags, or \code{nullptr} for the
periodic path, which is byte-identical to the unmasked code). Inside a
mask, out-of-region neighbours are replaced by the
Rohart--Thiaville/Bogdanov--Roesler ghost-cell extrapolation shared by
the exchange and DMI stencils, the field is zeroed outside the region,
and the demag magnetisation is zeroed before the convolution.
Single-layer mode (a lone ferromagnet) is selected by an empty bottom
layer; it uses \code{rk4_step_single} and requires no demag kernel.
These mirror the Python \code{mask=} / \code{m_bot=None} additions in
\code{fields.py}, \code{relaxation.py}, and \code{integrator_sllg.py}.

Each sweep script maps one-to-one to a C++ binary
(Table~\ref{tab:sweeps}).

The deterministic gates (\code{run_t0_nodemag}, \code{run_t0_demag})
verify that the zero-noise Heun stepper reproduces the deterministic RK4
(relative deviation $<2\%$ on diameter, drift velocity, and topological
charge; in practice the C++ runs agree to machine precision). The
statistical gates (\code{run_equipartition}, \code{run_langevin},
\code{run_brown_reversal}) validate the thermal physics against
implementation-independent closed-form targets---Rayleigh--Jeans
equipartition, the Langevin function, and Brown's high-barrier reversal
time. These cannot bit-match Python because the C++ noise generator
(\code{std::mt19937_64} with \code{std::normal_distribution}) differs
from NumPy's PCG64; they instead pass their own physics tolerances
(measured: equipartition median ratio $0.985$, Langevin RMS relative
error $0.015$, Brown $|\log_{10}|\le 0.16$). The deterministic analytic
targets ($L(x)$, $\tau_\mathrm{Brown}$, $H_k$) are parity-checked against
Python in the \code{test_validation} unit test.

\section{User guide: building and running}

\subsection{Dependencies}
CMake $\geq 3.20$; a C++17 compiler (AppleClang or GCC $\geq 9$); FFTW3
(double precision); the vendored \code{libnpy} at \code{src/aux/libnpy};
OpenMP optional (auto-detected). Installing FFTW3:
\begin{shell}
brew install fftw          # macOS
apt install libfftw3-dev   # Debian / Ubuntu
\end{shell}

\subsection{Build}
\begin{shell}
cd src/simulator_cpp
cmake -S . -B build
cmake --build build -j
\end{shell}
This produces \code{build/skyrmion_sim}, the thirteen \code{sweep_*}
binaries, and the test executables.

\subsection{Configuring a run}
There is no command-line parsing. Every run-time value is a named
variable at the top of \code{main()} in the relevant source file; edit
and rebuild. For the standalone simulator this is
\code{src/main.cpp}:
\begin{shell}
p.nx = 256;  p.ny = 256;  p.a = 2.0e-9;
p.dt = 5.0e-14;  p.n_relax = 10000;  p.n_steps = 5000;
p.pulse = std::make_shared<ConstantPulse>(4.0e11);
p.demag_kind = DemagKind::None;   // None | Slab | Newell
p.dump_snapshots   = true;
p.dump_every_relax = 200;
p.dump_every_drive = 100;
p.max_dump_frames  = 500;
\end{shell}
Then \code{cmake --build build -j \&\& ./build/skyrmion_sim}.

\subsection{Demag model}
\code{DemagKind::None} is the default local-$K_{\text{eff}}$ path
(slab demag folded into the anisotropy; matches the Python
\code{rhs_local_keff} production run). \code{DemagKind::Slab} applies
the analytic thin-film kernel via FFTW; \code{DemagKind::Newell} uses
the mumax3-style finite-prism kernel (set \code{demag_accuracy} and
\code{demag_tol_conv}; defaults 8.0 and $2\times10^{-2}$).

\subsection{Running the sweeps}
Each sweep binary has its grid baked in at the top of \code{main()}.
Run the whole grid serially, one grid point via a SLURM array index,
or many points in parallel with \code{xargs}:
\begin{shell}
./build/sweep_S42_J                                   # whole grid
SLURM_ARRAY_TASK_ID=3 ./build/sweep_S42_J             # one point
seq 0 8 | xargs -P 4 -I {} \
    env SLURM_ARRAY_TASK_ID={} ./build/sweep_S42_J    # local parallel
\end{shell}
Outputs land in \code{output/sweeps_S41_S49/<analysis>/}, the same
layout as the Python sweeps, so \code{studies/saf_racetrack/scripts/analyze_*.py} and
\code{studies/saf_racetrack/scripts/plot_*.py} read them unchanged (after the one-line
\code{load_trace} patch that accepts the C++ byte-encoded metadata).

\subsection{Running the stochastic scans and validation gates}
The stochastic experiment scans use the same dispatch as the sweeps: the
grid is baked into \code{main()} and \code{SLURM_ARRAY_TASK_ID} selects a
single point. Each writes a trajectory npz under the per-scan output
directory:
\begin{shell}
SLURM_ARRAY_TASK_ID=0 ./build/scan_tj          # one (T,j,ens) point
./build/pair_potential                         # whole r_init x ens grid
\end{shell}
The validation gates take no arguments (the configuration is at the top
of \code{main()}); each prints PASS/FAIL, writes its \code{.npz}, and
returns non-zero on failure so it can gate a CI step:
\begin{shell}
./build/run_equipartition && ./build/run_t0_nodemag && \
    ./build/run_t0_demag && ./build/run_langevin && \
    ./build/run_brown_reversal
\end{shell}

\subsection{Snapshots and animation}
Each grid point writes a per-frame observable trace
\code{<id>.npz}; when \code{dump_snapshots = true} it also writes
\code{<id>_snapshots.npz} containing the field history in the same
schema as the simulator. Replay either with:
\begin{shell}
python studies/saf_racetrack/scripts/animate_simulation.py   # edit npz_path at top of main()
\end{shell}

\subsection{Threading}
When OpenMP is present, per-site loops are parallel:
\begin{shell}
OMP_NUM_THREADS=8 OMP_PROC_BIND=close OMP_PLACES=cores ./build/sweep_S42_J
\end{shell}

\subsection{Tests}
\begin{shell}
python src/simulator_cpp/tests/run_tests.py
\end{shell}
This regenerates the Python references, builds, runs the 22 ctest
parity suites (deterministic simulator, sweep layer, stochastic
Stratonovich--Heun stepper at $T=0$, LCC connected-component
diagnostics, two-skyrmion pair IC, and the validation analytic targets),
then the Python error-contract and sweep-parity harnesses. All numeric
parity is at $\lesssim 10^{-12}$ relative error; the $T=0$ stochastic
stepper bit-matches the deterministic RK4.

\section{Profiling: C++ vs Python ($64\times64$)}

Both implementations integrate the identical workload --- a SAF
skyrmion pair on a $64\times64$ lattice, $2000$ RK4 LLGS steps after a
$50$-step warm-up, integration only (no I/O, no observables). Two
field models are timed: the local-$K_{\text{eff}}$ path and the slab
FFT-demag path. Tools: \code{tools/profile_run.cpp} and
\code{tools/profile_run.py}.

\paragraph{Environment.} Apple M3 Pro; AppleClang 16
(\code{-O3 -march=native}, single-threaded --- OpenMP not active on
this build); Python 3.12.5, NumPy 2.4.4, SciPy 1.15.2.

\begin{table}[h]
\centering
\caption{Time per RK4 step ($64\times64$, mean of two runs).}
\label{tab:profile}
\begin{tabular}{l r r r}
\toprule
Field model & C++ ($\mu$s/step) & Python ($\mu$s/step) & Speed-up \\
\midrule
local-$K_{\text{eff}}$ & $\approx 316$ & $\approx 2914$ & $9.2\times$ \\
slab FFT demag         & $\approx 1714$ & $\approx 7374$ & $4.3\times$ \\
\bottomrule
\end{tabular}
\end{table}

The local-$K_{\text{eff}}$ path --- dominated by per-site stencils and
cross products --- gains the most ($\sim 9\times$), since the C++ loop
fuses the field terms and avoids the temporary arrays that NumPy
allocates per operation. The slab path is FFT-bound; FFTW (C++) and
SciPy's pocketfft (Python) are comparable, so the speed-up narrows to
$\sim 4\times$. With OpenMP enabled the local path would scale further
on the per-site loops; FFT scaling at $64\times64$ is limited.

\paragraph{Caveats.} Single trial pair, single thread, small lattice;
absolute timings depend on hardware and library builds. The comparison
is meant to show the order-of-magnitude advantage of the C++
integrator on the stencil-bound path, not a tuned benchmark.
